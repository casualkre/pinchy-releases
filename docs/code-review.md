# Code review: find what is wrong in a project

Code review reads a project for real problems (crashes, wrong results, lost data, security holes), runs the project's own checks, tries the app itself on Pinchy's own desk, and shows you what he found. You decide what gets fixed: he only shows, lets you pick, or fixes the sure ones on a branch of their own. It has its own window, separate from the Workspace.

## What to ask for
- "Review my notes app for bugs." He opens a review of that folder.
- "Check only what I changed on this branch." A review of the changes, not the whole project.
- "Look especially at the login flow." What you say goes to every reader as the focus.
- "Review https://github.com/owner/name." A repository by its address, without cloning it yourself.
- "Review my lobster repo and test it at https://my-site.example.com." The source from GitHub, the running website tried on his desk.
- "Fix the two high ones from the review." One code krill fixes exactly those, on its own branch.
- "Review https://github.com/owner/name/pull/12." Only what that pull request changes is read; you can post the findings on it afterwards.
- "Review the rest of Pinchy." The next review reads the files no earlier review of that project read, or that changed since.
- "Have the Coder agent review the api-server every Friday." Agents can start review jobs too; their reviews show in the same window, tagged with the agent's name.

## How it works
- Where: the Code review window. Open it from the tray menu (Code review), from his right-click menu (add the Code review tile when you customise it), or just ask him.
- The start page: pick a folder on this computer (recent folders are offered) or a repository (pick one of your own from the list, or type its address: https://, ssh:// or git@host:path, an optional branch), the whole project or only what changed, what happens when he finds something (Just show me, Let me pick, Fix them too), whether he tries the app, and how deep he reads (Quick reads the riskiest parts, Deep uses several readers and desks at once). An optional line says what to look at especially.
- The stages show at the top while it runs: Looking around, Running its checks, Reading the code, Double-checking, Trying the app, Writing it up, and Fixing when you chose Fix them too. The bar under them is how much of the code has been read.
- What he reads first: the project's own code before scripts, tests and test data; among those, what no earlier review of the project read (or what changed since), and what changes often for its size. A big file is read in parts (each reader gets its own lines and a list of what the rest of the file holds) instead of being skipped. Files that are generated or minified are skipped, and so is any link that points outside the project. Each part is read for what that kind of code most often gets wrong first (input from outside, ordering and timing, what the screen shows, data that is kept, plain wrong results, calls between files) and every other real problem too; a Deep review reads its busiest parts twice, through two of those lenses.
- Security review: a fourth choice next to Quick, Normal and Deep. He reads the ways in first (web routes, messages between windows, logins, file and shell handling), reads every part the way an attacker would and says for each problem how an attacker gets to it; the report groups them by that way in. Tick "Look the dependencies up online" and he also checks the versions in your lock file (package-lock.json, or a fully pinned requirements.txt) against the known-vulnerability lists — only the lock file is looked at, nothing is installed or run. Only you can tick that, not an agent.
- Before you start: once a folder is picked, the start page says how much this review will read (files, parts, how long, and — from your own earlier reviews — about what it costs). A big project is not read whole at once: "Review the rest" reads what the last reviews did not, so it is covered over a few reviews.
- Every file, without running it: before the readers start, each file in scope is checked for broken syntax, imports of files that are not there, leftover merge conflicts and secrets written into the code. Nothing of the project runs for this.
- Its checks: your project's own test, lint, type check or build run in a throwaway copy of the project. Your folder is never touched, and uncommitted changes are part of what is reviewed. A failing check is a finding.
- Double-checking: a second reader tries to prove each finding wrong before you see it — it follows the code from where the problem starts to the line that goes wrong and says how sure it is, the path it followed and how to make it happen. What it disproves moves to Dropped; what it could not prove but thinks likely is marked Likely. The line each finding points at is checked against the file itself: the code you see in the window is the real code, and a finding whose quoted code is not in the file is never shown as confirmed.
- The same mistake elsewhere: once a problem is confirmed, he searches the whole project — files no reader had too — for other places with the same mistake, double-checks those, and shows them together with the first one.
- Only what changed: a review of a branch's changes also shows the readers where the changed functions are used, so they check the callers still work.
- Your repositories: with GitHub connected (Settings → Add-ons → Connectors → GitHub, or `gh auth login`), the start page lists your repositories, newest first, private ones marked with a lock; type to search, click one to pick it. A private one is copied with your GitHub login, which is never written into the copy, the address, the report or the log.
- The app itself (optional): next to the source, give the app to try — "Find it in the code" (he starts it from the project), "A website" (its address; he opens it in a fresh browser on his desk) or "A program file" (an .AppImage, or a Windows .exe that runs through Wine on his desk). When you give the app, it is always tried, even for a repository he only reads, because nothing from the repository runs. On his desk a program can see your files and go online (not your browser, mail or chat data), and what it writes is thrown away — pick only a program you would run yourself. The program file has to be in your home folder, and only you can pick one in this window — an agent's review can give a website, never a program. The review's header shows what was tried. A Windows .exe needs Wine on this computer (without it the review says so), and where his desk can't run (your away server, Windows, macOS, Linux without KDE Plasma 6) Pinchy's VM can only try a website.
- Trying the app: when the project has a window or a web page, he starts it on his own hidden desk (several desks when the review is Deep) and clicks through it. You can watch each desk live in the review window and click one to open it big and take over its mouse and keyboard. Whatever the app writes there is thrown away when the review ends.
- The quick click-through (websites and web apps): before the tester looks, his desk's browser clicks every safe button, tab and link of the app once, with no model — never Delete, Pay, Send, Save, Sign out or a form that posts — and every error the page throws, every request that fails (404, 500) and every file it could not load becomes a finding that says which click caused it and in which file, with a picture of the first screen. What it found is the tester's first list to try. A real website you gave is only watched, never clicked by it.
- The overview at the top of a review: how many problems (High, Medium, Low), what kinds (click one to show only those), how much of the project was READ (a big project at a quick depth is only partly read — the ring and "N files not read" say so honestly), how sure the findings are (facts from failing checks, code tools or the running app; confirmed by a second reader; likely), the project's own checks, how long it took and what it cost. When you reviewed the same folder or repository before, it also says what is new and what went away since then ("Only the N new" shows just those).
- The findings: sorted by how bad they are, or by file, kind, cause, or what he looked for. The same problem found in several places is one finding with "+N more". Click a finding and the right side shows it in full: what is wrong and how it fails, the code around it with the line marked, how it was checked (step by step, and how to make it happen, when he knows), the screenshot for the app, and its buttons. Click the file and line (or press o) to open it in your editor; Copy puts it on the clipboard as Markdown for an issue or a chat.
- Before you start (a folder): the start page says what he will read and roughly what it costs — "Reads 412 of 2,360 source files (17%) · 31 parts · ~25 min · about $3" — guessed from your earlier reviews. A big project is read over several reviews: tick "Only what earlier reviews did not read", or press "Review the rest" under the read ring of a finished review.
- A pull request: pick "A pull request" and paste its GitHub address. He reviews only what it changes (and the code it touches) in a throw-away copy. Nothing goes to GitHub until you press "Post on the PR": you first see exactly what will be posted (a comment on each changed line it is about, the rest in the review's text), with your GitHub login, as a comment — never an approval. Posted findings say "On the PR".
- Teaching him: 👍 Good find tells his next reviews of this project to look for that kind of problem; Not a problem tells them to leave that kind alone. Both go into this project's review rules ("Learned here: N rules" in the overview) — you can delete a rule or edit the file by hand.
- After a fix: he checks the fixed findings again on the fix's own branch — "Closed ✓", "Still there" or "Re-check unclear" on each, and the hand-over says how many closed. "Check again" runs it once more.
- Ask Pinchy (on a finding): his chat opens with the finding attached — what is wrong, where, the code, how it was checked — so you can ask why it is a bug or how to fix it. Nothing is sent until you type.
- Watching a project: on a folder's review, choose "Review every night" or "Review after every push". He then reviews only what changed since the last review, by himself, and tells you only when a NEW high problem shows up; the results wait in this window. Off for every project until you turn it on.
- Keys in a review: j / k (or ↓ / ↑) walk the findings, x ticks one for fixing, o opens its file, / searches, Esc clears the kind / area filter.
- Areas: the readers split the project into areas. While he reads, the Areas tab shows them lighting up one by one; afterwards it is the map of what was read and where the problems are — click an area to see only its findings. A narrow window shows the findings opening in place instead of on the right.
- Fixing: tick findings and press Fix selected (or Fix this on one). That starts one code krill on its own branch. When it is done the finding says Fix ready, and the bottom of the window has Apply, Keep as a branch and Throw away. Nothing reaches your branch until you press Apply.
- After a fix: when the fix job is done, the review checks the fixed findings again on the fix's own branch and marks each Closed ✓ or Still there (Check again does it once more).
- Not a problem: dismiss a finding and say why if you like. It moves to Dropped, and the next review of the same project is told, so the same thing is not raised again.
- He learns what you want: 👍 on a finding (a good find) or 👎 / Not a problem (not a bug here) becomes a line in this project's review rules, which every reader and the checker of the next review read. They are your preferences: they can make him skip a kind of finding you do not want, never make him keep quiet about a security hole, a crash or lost data. Open the rules file from the review to read or edit it by hand; each learned line says when you voted.
- A pull request: give its address (https://github.com/owner/name/pull/12). He copies the repository, takes the pull request's own commits and reads only what it changes against the branch it goes into, with the code around it. The header shows its title and author. Tick findings and press Post on the pull request: a preview shows exactly what will be posted — one review, a comment on each finding's line when that line is part of the pull request, the rest in the review's text — and only your click posts it, with your GitHub login, as comments (never an approval or a request for changes).
- A repository: he copies it just for the review (a shallow copy inside the review's own folder) and throws the copy away with the review. By default he only reads it — it is someone else's code. Tick "Run its tests and app" on the start page to let him install it in the copy (install scripts off), run its tests and try the app on his own desk.
- Running a repository's code is sealed off: its install and tests run in a box that sees only the copy — your home folder, your keys, Pinchy's data and your tokens are out of reach, and nothing it writes outside the copy is kept. That box needs Linux with bubblewrap (bwrap); on Windows, macOS or a Linux without it the review reads the code only and says why.
- Only your own tick runs a repository's code. When Pinchy or an agent starts a review of a repository address ("Review https://github.com/…"), it is always a read-only review; tick the box in the window yourself if you want its tests run. A fix of a repository is written but not run or tested (it is someone else's code) and leaves as a draft pull request (GitHub signed in, gh auth login, and push rights) or a .patch file you save. A private repository works when GitHub is connected or your own git already knows the login.
- The report: every review writes a REPORT.md with all findings, the checks and what was read. Report in the window opens it.
- When Claude is busy: the line under the stages says so ("Claude is overloaded — trying again (2/10) in 8 s") instead of looking stuck.
- No code, only the app: a folder without source code where you gave the app itself (a website or a program file) is a review of the app alone — he tries it on his desk and what he sees are the findings.

## Settings
- The model that does the review is the one for Code krill: Settings → Workspace → Code krill.
- Trying the app needs Pinchy's own desk: Settings → Computer → Pinchy's own desk. When it is off or cannot run on this computer, the review says so and reviews the code only.
